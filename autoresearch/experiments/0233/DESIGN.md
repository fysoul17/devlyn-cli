## Submission, diagnostics, decision

All arms use the same locator: one accepted task-complete receipt bound to an accepted commit wins; otherwise the single product-changed live tree wins (anchor or linked worktree), or the unchanged anchor. Two accepted receipts or multiple changed trees without acceptance STOP. `snapshot.json` records the selection rule; other trees remain for audit.

`diagnostics.json` reports guide and delivery reads and `task-complete.py` calls from owner tool events, including call position, first edit positions, subcommands, and observed exit codes. A and B report guide `absent`. A guide call is `read` only when its successful tool result contains `# Changes that hold state or resources`; naming the path alone is `mentioned`. First-read timing uses the first successful content read. These observations never affect grading or admission. Expected guide applicability is a registration judgment supplied by root, not inferred from outcomes.

Owner-launched `codex exec` and `claude -p` sessions are every traced Codex session and Claude transcript other than the registered owner and its native children; 0233 registers no worker or judge seat, so saved legacy captures (`*.output.json` envelopes, plain-mode `*.stderr` headers, dispatch records) feed usage accounting only and never impose a model. Their engine, model, and effort are reported in the verdict. Their usage counts once by thread or session id; missing usage is a named gap or labeled transcript lower bound. Their models, and any `model_reroute` in their sessions, do not change the registered owner's strict identity verdict; a reroute in the owner's or a native child's session still does.

Oracle record comparisons use `node:util.isDeepStrictEqual`, so a writer's property order never fails a row (`calibration/F10/good-key-order`).

`screening.tsv` has 16 unscored A/B cells. For each task/config, any of its four screening cells with incomplete product or a failed oracle row creates confirmation headroom. Otherwise the matching confirmation cells in `cells.tsv` write `NOT_RUN` verdicts. `cells.tsv` freezes 48 development, 12 easy, and 24 confirmation slots. `smoke.tsv` has six route cells. Development and confirmation blocks run three arms back to back, with reversed blocks and arm order in replicate two; each development configuration sees all six arm orders.

`decide.py` applies 0232 §6 separately to development, eligible confirmation, and easy. Eligibility and confirmation operate per configuration over that configuration's eligible tasks. It reports B/A, C/B, C/A for each panel. Confirmation is `FAIL` for any C/B or C/A quality failure on any eligible task, a failed comparison, or zero C successes against any A/B success; both comparisons passing gives `PASS`; other nonempty panels give `UNCONFIRMED`. An empty confirmation panel is `NO_HEADROOM`. It admits C in a configuration only when development C/B and C/A both PASS and confirmation does not FAIL; `UNCONFIRMED` and `NO_HEADROOM` admit `C-unconfirmed`. Easy completion regression or a C raw wall/input/output total above 1.25× B is a reported tripwire only. Unknown usage remains unknown. Screening cells enter no sum.
