# Single-peer design review v1

**SHIP-for-testing**, with no blocking HIGH in the proposed design. This is prospective research design approval only: implementation, actual native enforcement, transport acceptance and efficacy remain unverified. No model/auth/native CLI/test calls or frozen-input changes were made for this review.

A pair can legitimately mean one implementation owner and one independent primary-model reviewer. Removing delegation from the reviewer is a smaller, intelligible mechanism; it retains the counterexample search, independent primary context/model, executable findings and owner verification. The observed cancelled peer inference supplies a concrete reason to bound this mechanism. **No overengineering** favors the supported stable multi_agent setting over an under-development mailbox-preemption change. **No workaround** requires retaining the original STOP/UNKNOWN and naming the capability change, rather than asserting that missing usage has been repaired.

The strongest objection is that this is a real treatment change prompted by an accounting failure, not a measurement repair or demonstrated quality improvement. A solo peer loses parallel coverage and its child’s potentially independent check; fixed watchdog time may exacerbate that loss on larger tasks. Disabling a cheaper native child also changes the resource mix, with no justified claim that total tokens or time decrease. Claude already lacks child tools, so this reduces one asymmetry without making the engines’ full tool capabilities equal. Register the new treatment explicitly and do not pool the old child-enabled smoke as equivalent evidence.

The retained metadata probe establishes pinned native feature recognition: multi_agent is stable and switches true→false via the proposed configuration; defer_mailbox_preemption is under development. It does not establish the actual model-visible tool catalog. A configuration override is stronger than a prompt alone for native delegation, but it is not a universal prohibition on launching another CLI from an executable tool. Keep the existing no-independent-recursion contract and inspect captures/process evidence for prohibited nested sessions. Do not add a broad new sandbox framework without an observed need.

Most importantly, owner native children remain enabled. The same cancellation/accounting gap could therefore recur in an owner session, and cancellation can have other causes even without children. This design removes the observed peer-child path; it does not guarantee complete accounting. Preserve the unchanged whole-run guard and STOP on any remaining unknown usage. Do not suppress cancelled events or reinterpret equal cumulative totals as zero cost.

## Smallest justified validation

1. Before any native call, verify the exact Codex peer fresh **and resume** argv contains `-c features.multi_agent=false`; the override must not reach the owner configuration. Seal changed helper/guides/tasks/packages and retain the old experiment identity. Review targeted command-construction/control results rather than rerunning unrelated suites.
2. Run one newly identified native Codex-peer fresh+same-session-resume smoke at the unchanged primary model/max effort. Inspect captured request tool definitions, effective configuration and thread/session trace: no native child tools, no delegated threads, complete primary usage, valid final answers, source stability and clean teardown. Metadata output alone and mere absence of a spawn call do not establish tool removal. Preserve the operational task’s original calculation semantics while removing only its explicit must-spawn-child clause and adding the prospective capability assertion.
3. A successful Codex-owner→Codex-peer smoke validates the changed peer transport and permits targeted reuse for the same helper branch. Claude-owner→Codex-peer still needs its first route-specific native evidence, because owner environment inheritance differs. Codex-owner→Claude-peer also needs its first route-specific evidence if not already accepted; the feature flag does not justify repeating it if unchanged and already proven.
4. Previously accepted Claude-owner→Claude-peer evidence can be reused **only for unchanged transport facts**: Claude argv/tool restrictions, fresh/resume, identity, capture and teardown. It cannot be relabeled as execution of the new guide/package seal or as efficacy evidence. If a changed guide changes the actual launcher contract, revalidate that changed behavior; otherwise a full repeated H-Claude model smoke adds little. Product-effectiveness measurement begins only after the revised treatment and comparison are registered.

A failed new smoke remains visible and stops dispatch. Fresh post-change identity is justified by a named treatment revision, not by a rule to reroll until accounting happens to pass. No broader runtime/accounting change is needed to test this hypothesis.
