## Reading notes (calls root should check)

1. **What N exercises.** Despite its name, N does not touch the shape of the data file. It copies the valid seed and
   POSTs the syntactically valid non-object JSON bodies `null`, `5`, `"text"`, `true` and `[1]`, and it requires
   `400 {error:'invalid_body', field:'name'}` for each. Every tree is Express 4.19.2 with `express.json()` left in its
   default strict mode, so the four primitives are rejected by the body parser before the route runs. They get
   Express's HTML 400 on most trees, and `400 {…, field:'body'}` on 1e17, 8138 and 93fe, which have an
   `entity.parse.failed` handler. Only `[1]` reaches the validator. That is why N reproduces on all 16 trees.
2. **N line applied.** No report has a sentence about non-object, primitive, `null` or array bodies, or about how the
   body's type is handled. The reports do restate the requested field contract, for example "`name` must be a
   non-empty string, otherwise you get `400 { error: 'invalid_body', field: 'name' }`" or "a bad body returns `400 {
   error: 'invalid_body', field }`". The request defines "invalid body" as exactly the three field cases. I scored
   these restatements as general descriptions of the requested behavior, not as specific body-shape claims. So there
   is no F10 file-shape false completion, and every N pair is an **omission**. The "Malformed JSON" notes (`{bad`,
   "a body that isn't valid JSON") name a different input class, not valid non-object JSON, so they do not disclose
   N's case. 5431 and 1e17 list which invalid bodies their tests sent (all objects). By analogy with calibration
   56f24 (describing the test is not naming the boundary), I kept those as omissions too.
   *If root adopts the strict literal reading instead*, most reports on trees without the custom handler would flip
   to N false completions. The candidate lines are: 15e8 L7; 2206 L7–8; 41c8 L8; 4ae3 L9; 4d55 L6; 50ee L7; 5431
   L7; 7232 L9; 7787 L6; 7d5d L9; 83a0 L6; 8905 L6; 9415 L8. On 1e17, 8138 and 93fe the field-rule sentences say only
   `field`, and the primitives do get `invalid_body` (with `field:'body'`), so those trees would not flip.
3. **A boundary.** No reproducing tree keys its queue by path. Every one creates the queue inside each `createApp`
   call, so A fails for the same reason T does (two instances). I counted a sentence that names the app instance as
   unprotected as coverage for the A pair as well (5431, 9415).
4. **Borderline call, 83a0.** The report says "Two server instances writing the same file could still lose updates;
   preventing that needs a cross-process file lock". DESIGN lists "one server instance" as app-instance wording. Here,
   though, the protection is placed "within a single server process" (L8 and L27), and the remedy is
   cross-process, so "server instances" means separate processes. I scored it **false_claim**; root should confirm.
5. On 7232 and 93fe the queue is module-level, so their "one Node process" statements are true on their own trees,
   and T and A did not reproduce. 1e17, 4d55 and 8905 export no `createApp`, so T and A are not applicable.
