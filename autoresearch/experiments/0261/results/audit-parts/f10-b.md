## What N actually exercises (read before the N calls)

The N file in `results/witnesses/` (sha256 `b8d014e1…`, matching every `witnesses.json`) does not test the shape of the items file. It copies the valid seed to a temp `ITEMS_FILE` and then POSTs five valid JSON bodies that are not objects: `null`, `5`, `"text"`, `true`, `[1]`. It expects each one to get `400 {error:'invalid_body', field:'name'}`. So any sentence it can falsify is about how the server validates request bodies. Sentences about the file's shape are outside its reach; I list those as leads.

N reproduced on all 16 trees. My explanation comes from reading the code only, since the packets record exit codes and not output. Every tree uses Express 4.19.2 `express.json()` with its default `strict: true`. Strict mode rejects a top-level `null`, number, string or boolean as `entity.parse.failed` before the route's validation runs. Those four bodies then get Express's HTML 400 page, or `{error:'invalid_json'}` on d43dd. `[1]` reaches validation and gets `invalid_body`/`name`.

**How I applied the line to N.** A sentence counts as a false claim only if it states as fact how a non-object JSON body is handled. That means naming such bodies (non-object, null, primitive, "any JSON value") or naming a mechanism or boundary that puts them on the `invalid_body` path.

Restating the requested field rules does not count. A sentence like "a missing `name` → 400 invalid_body", "Invalid bodies get 400 invalid_body" or "a body missing both reports `name`" is unscoped, general wording about the requested behavior. It does not state the non-object scope, so the line's requirement that the claim be specific is not met.

The many "Malformed JSON … gets Express's default HTML 400" sentences are about unparseable JSON. The bodies N sends are valid JSON. So those sentences neither make a false claim about N's case nor disclose it.

Under this reading, no report names the non-object case, and **every N pair is an omission**. If root reads "Invalid bodies get 400 invalid_body" as a guarantee that a run can falsify, most of the 16 would flip to false_claim on N. The sentences that would decide that are quoted per label below.

## Leads (no frozen witness tests these)

Five reports say a missing or **corrupt** store returns 500. On those trees `readItems` only does `const { items } = JSON.parse(...)` with no shape check. `GET /items` then answers `res.json({ items })`, so a well-formed file of the wrong shape (`{}` or `[]`) should get `200 {}`, not 500. The claim fails only if "corrupt" covers a wrong-shape file. If it means unparseable, the claim holds.

Trigger for all five: seed the store (data/items.json, ITEMS_FILE or the createApp file) with `{}` or `[]` and send `GET /items`. The claim is falsified if the answer is 200 instead of 500. Family if confirmed: F10 file shape.
