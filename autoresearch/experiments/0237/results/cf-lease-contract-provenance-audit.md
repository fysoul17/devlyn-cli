# CF-LEASE revision-2 bundle: read-only oracle provenance audit

2026-10-10, before any CF-LEASE model run. No gold implementation or control success is used as proof of a requirement. No tests/models were run; fixtures, frozen inputs and outcomes were not edited; active f05 was not inspected.

Base path for all references: `autoresearch/experiments/0237/confirmation/CF-LEASE/`. `O` below means `hidden/oracle.py`, `D` means `visible/docs/delivery.md`, and `S` means `visible/docs/storage.md`.

**Finding:** the oracle is not wholly supported as an unconditional binary admission gate. One assertion clearly strengthens the token contract across different jobs. A database-error injection also relies on a particular internal write path. Two smaller output-format expectations have weaker provenance than their parent behavior. Most lifecycle assertions have explicit, unusually precise public support.

## Unsupported or ambiguous expectations

1. **Global token uniqueness across distinct jobs — unsupported strengthening.** `O:132` demands eight different tokens for eight different job IDs. `D:9` requires a new token when **reclaiming a job**, including reuse of its worker ID; `D:14–16` prevents two connections receiving the same attempt. Neither requires tokens to be globally unique across distinct jobs. A per-job generation token, combined with job ID and exact receipt fencing, can meet those promises while using the same token text for the first attempt of different jobs. This is a conceptual counterimplementation, not an executed test. The existing `uuid4()` in `visible/parcel/leases.py:15` supplies global uniqueness but is an implementation choice, not an expressly preserved token format/uniqueness contract. The manifestation's quoted binding to “Independent SQLite connections” does not justify this extra assertion.

2. **Settlement fault injection assumes `UPDATE jobs.state` — internal implementation dependence.** `O:185–186` installs a trigger specifically on updates of `jobs.state`, and `O:188–193` requires that trigger to fire. The public requirement that settlement/database errors escape is explicit (`D:27–28`), and transaction rollback is explicit (`S:12–13`). The precise SQL write operation and table layout are not listed as public APIs (`S:19`). An equivalent atomic persistence implementation using a different write path could miss the trigger while preserving the stated external behavior. The direct `Store.connection`/schema access is visible in baseline source, but its immutability is not promised. Thus the behavioral obligation is valid; this injection's applicability depends on retained internals. An exception while installing the trigger is also caught by the outer `check()` as product FAIL, rather than distinguished as an inapplicable probe.

3. **Exact worker diagnostic serialization — source-supported, document-ambiguous.** `O:177` requires exactly `'delivery timeout'` from a raised `RuntimeError`. `D:19,23–25` requires recording diagnostic text and reporting retried/lost, but does not define an exception-to-text format. Baseline `visible/parcel/worker.py:12–14` passes `str(exc)`, and `leases.py:35` stores `str(error)`, so preserving that existing behavior is a reasonable compatibility reading. An informative prefixed diagnostic could satisfy the prose yet fail exact equality. This is weaker provenance than the direct `retry(..., 'temporary failure')` echo at `O:90`, which receives that diagnostic text as an explicit API argument.

4. **Job ID on newly required `lost` worker result — plausible, not explicit.** `O:147` additionally requires `result.job_id == 'invoice'`. `D:25–26` expressly requires state `lost`, but says nothing about its job ID. Existing completed/retried results populate it (`visible/parcel/worker.py:14–15`); `ProcessResult` exposes an optional field defaulting to None (`model.py:24–27`). Extending the existing populated-ID convention to lost is sensible, but the docs do not state that extension. This should not be confused with the explicitly specified lost state itself.

## Timing and evidence boundaries

The fractional boundary comparisons and `now + delay` arithmetic follow the explicit public time contract; there is no hidden rounding or integer-only convention. However, `O:126` imposes a **10-second thread-start barrier** unrelated to a product latency requirement. A broken barrier, inability to start threads, or other probe setup failure can be captured as row FAIL by `O:8–14`. Those must be distinguished from an observed fencing defect if encountered; passing gold once does not rule them out. This audit did not execute the concurrency probe or assess its runtime stability.

Most rows call exported package APIs; there is no direct private-helper ownership assertion analogous to CF-CONFIG's merge-result detachment. The main internal dependency is the settlement trigger above. Contract bindings in `hidden/manifests.json` name relevant parent requirements but do not automatically cover every subordinate assertion.
