## Smallest actionable hypothesis

Trigger on an observable kind of change, not an owner's declared impasse: **ordering or identity derived across representations, or ownership/recovery transitions in shared state**. Run the additional check after the owner has a stable implementation and its ordinary checks, even when the owner sees no remaining issue. This narrows 0234's generic multiple-rules/shared-state trigger and changes its three-turn co-design recipe into one independent counterexample attempt on a stable source.

Draft mechanism text, not an installed instruction:

> Before completing a change that derives ordering or identity through parsing or storage, or changes acquisition, recovery or release of shared state, obtain one fresh read-only peer check of the stable candidate. Give the original request and relevant raw source, diff and check results before your interpretation. Ask for an executable counterexample tied to the visible contract. You alone reproduce supported findings, repair them, and recheck the affected invariant and neighboring behavior.

One peer check is a falsifiable reduction of the old recipe, not a proven sufficient turn count. No fixed token allowance or new timeout is proposed; existing watchdogs and complete accounting apply. No mandatory peer closure follows a clean response. A timeout, inability to inspect, or inability to execute a probe is reported as such, not converted into a clean review. A proposed but unexecuted counterexample is a prediction until the owner executes it. Use the actual-model route and sole-writer controls in `pair-apparatus-plan.md`; same-engine native subagents cannot silently replace a registered same-model independent peer.

The trigger need not be a slash command. A conditional root instruction can activate it without user typing. Do not introduce a classifier, score, task-size rule or orchestration phase. It adds to existing consequential-path obligations; it does not replace them. The owner can still misclassify a boundary, so activation sensitivity and overhead remain measured outcomes.

## Defensible comparison, without a new apparatus

Use the same accepted solo baseline and original request in every arm. Select eligibility from visible source/contract risk and remaining solo headroom before dispatch; never feed hidden findings to the owner. The smallest useful contrasts are:

| Arm | Extra step after ordinary solo work | Question answered |
| --- | --- | --- |
| B | None; best admitted solo instructions | Does any added mechanism improve end-to-end outcomes? |
| S | Owner receives the same scoped counterexample instruction and continues in its existing context | Does a deliberate additional verification attempt suffice? |
| H | Fresh read-only independent session of the owner's exact model/effort | Does an independent context add value over S? |
| P | Same protocol as H, changing only the registered peer model/engine route | Does model diversity add value over H? |

This need not become a large four-arm panel: first establish whether S or H produces useful residual gains, then test P against the stronger relevant control. Freeze that sequence before outcomes, not after choosing a winner. Keep an accepted-solo B comparator; a historical B draw is not a matched control if model, prompt or task conditions changed. A claim that the full harness beats native still needs a contemporary native comparison; H/B alone cannot establish it. Equal instructions and existing watchdogs do not imply equal compute: charge and report actual total wall, processed input and output, including selection, idle peer waits, failed calls, repairs and rechecks.

Record activation separately from peer findings, reproducible new defects, repairs, regressions, final complete product, identity and usage validity. Report all assigned runs including untriggered ones; comparing only activated successes biases the estimate. Keep easy controls with no qualifying boundary, and bounded multi-module controls with a decisive existing oracle, to expose false activation and root-instruction overhead. Stable source binding matters: in F23 the first peer's pre-implementation snapshot became stale during owner edits. In the proposed check, pause owner edits until that read-only pass returns, then bind any executed finding to the same source before repair.

F23, 0175 and 0185 are exposed development diagnostics, not confirmation tasks. Use oracle-audited untouched tasks and repeat draws for confirmation; do not recycle known witnesses as hidden successes, and exclude invalid oracle tasks such as UA1 rather than silently regrading. No model calls or new benchmark authoring are part of this audit.

The candidate is rejected or narrowed if the automatic rule mostly misses qualifying changes, triggers on easy controls, fails to reproduce a repair advantage over additional solo verification, introduces a consequential regression, or cannot meet the predeclared whole-run quality/resource criteria. The current evidence supports testing independent falsification; it establishes neither a solo ceiling nor a default cross-model advantage.
