# Root independent analysis — harness2 vs devlyn-cli (sealed before reading any reviewer output)

Written 2026-10-20 after reading harness2 core/prompts.py, recursion.py, library.py, ledger.py, selection.py and the paper (§2–4, App. E).

## What harness2 is
Per-task, test-time harness refinement without a ground-truth verifier: k base rollouts → k INV-scoped + k DOM-scoped editors edit the harness tree on disk (citing trajectory moments) → each candidate probed once on the SAME task → k composers merge/adopt/KEEP_BASE from contrasts → finals run → blind selector picks a deliverable (k>1) → reflector writes per-edit verdict rows (helped / hurt / no observed effect / confounded) and ≤1 transferable lesson (cue/lesson/evidence/confidence) or NO_ENTRY → per-domain library (full adopted tree + EXPERIENCE.md + INDEX.md) read by later tasks. Budget R=4k rollouts, P=3k sessions per task; 10–100M tokens/task.

Measured: +4.5 JobBench, +11.5 WorkBuddy, +11.8pp LAB; monotone in k. Ablations: library −3.1/−1.8, INV/DOM scoping −2.9/−3.7, composition −1.6/−1.9. Component value in adopted harnesses: skills −5.3, scripts −3.7, prompt group −1.5. Editing WITHOUT execution evidence degrades (code 73.4→63.2). Same-model editor works (Opus 5 +3.3/+5.5/+3.0). Weaker executors gain more. Tool-error rate −20…−37%. Failures: blind selection picked 55 over 95; a wrong premise propagated across all candidates; outcome variance confounds attribution.

## Reject for the product
1. Runtime Propose–Probe–Compose (4k rollouts per task). Breaks the owner's ladder rule (tokens never increase); 0234 measured pair/extra reasoning at 2.3–3.5× input with no completion gain. Harness2's premise is "no verifier"; our tasks carry mechanical acceptance (spec.expected.json, tests), so the contrastive no-verifier machinery buys less.
2. Blind deliverable selection, per-domain libraries of full harness trees: we do not produce k candidates, and the product is one methodology across repos.

## Leverage, ranked
1. (PROCESS — strongest fit) Change how WE generate harness candidates. Our recent line (0235, 0236, rp-d1…rp-d8) was almost entirely one always-on/near-always-on prose sentence per iteration, n=4–8, mostly INCONCLUSIVE/MIXED/REJECT. Harness2's evidence ranks prose as the weakest and the only always-paid lever. Adopt: (a) form-first candidate choice — skill/helper-script output/hook before prose; prose only for a short rule that applies to every run, paid for by a cut; (b) every edit cites a trajectory moment; (c) divergence-first diagnosis — act on failures that repeat across replicates, treat 1/k as noise; (d) INV vs DOM scoped proposals from the same evidence, probed on the same failing cell, then composed; (e) reflection rows with a `confounded` verdict and NO_ENTRY allowed. Smallest step: a playbook section in autoresearch/playbooks plus applying it to the next candidate. Risk: low (docs). Counter: we already do (b)/(c) informally; value is in (a) and (d).
2. (PRODUCT candidate, measured) "Ignored invariant → tool-loop lever". Harness2 INV template: only repeated evidence that clear prose is skipped justifies a defensive hook, and it must not block valid completion. We have that evidence for default delivery (rp-d5/d6/d7 Claude high ~2/4; 4.2.23 note Y 8/8 vs 6/8 inconclusive) and real-world helper bypass (helper covers 15–76% of owner-merged PRs, bypass after compaction). We already measured Stop-hook pressure works on Claude (0074/0078: block honored 5/5, converted a would-be incomplete into completion), retired only because it was bound to resolve state. Candidate: a one-shot Stop nudge when the session leaves undelivered changes ("deliver per task-completion.md, or state the explicit limit"), honoring stop_hook_active. Cost: zero always-on tokens. Blockers: product default (installs settings → Astra + owner), must not block valid stops (questions, explicit limits, pre-existing dirt → needs a session baseline), Codex hooks route was disabled by codex-monitored.sh policy in 0074. Status: candidate for owner decision + rp-d measurement, not a direct ship.
3. (PRODUCT, deferred per owner order "minimal solo first, pair earned, ideate deferred") ideate plan writes VERIFIED workspace facts (anchored "at base_sha …": exact paths, entry points, test command, conventions) into each spec.md instead of procedure to rediscover them. Harness2 GENERALIZE block: "the mapping itself removes the hardest step". Zero always-on cost (package-format.md is read only while planning). Predicted: lower executor input/wall, no quality change. Needs an observed rediscovery cost first.
4. (MEASUREMENT hygiene) Harness2 failure analysis → our apparatus: probes that challenge a shared premise, and replicate counts big enough to separate effect from variance (our +2 vs +3 margins). Also judge prompts: "unmodified is a valid pick", "length/polish are not merits".

(STRATEGIC question for the owner) Harness2 tailors the harness per executor; our CLAUDE.md == AGENTS.md. 0233 found 4.2.0 helps Codex (9/12 vs bare 6/12) and hurts Claude (3/12 vs 7/12), never re-measured. Harness2's cross-model transfer is positive but weaker than in-model refinement. That supports re-measuring Claude block-vs-bare first (the 0253–0255 accounting work was built for it) before adding anything to Claude's path.

## Not worth it
Evidence-is-data boundary for drain workers (generic), trigger-line lint (we have lint), cross-task lesson carrying inside an ideate drain (no observed failure; executor can read merged code).
