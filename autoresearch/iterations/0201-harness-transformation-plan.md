## 왜 비전으로 수렴하지 않았나

다음은 기록에서 도출한 운영 진단이다.

- **다음 연구 문제가 제품 이정표를 대체했다.** 0200 HANDOFF는 다음으로
  “supported core failure or untouched natural comparison”을 남겼다. README의
  다음 queue는 4월 0018–0022, MISSIONS Open work는 9월 6일 상태였다.
  0196→0197/0198 연구 뒤 0199/0200 수리가 이어졌지만 새 실행 구조의 채택 종료점은 없다.
- **구성요소 수리와 실제 작업 성능이 같은 진행축으로 보였다.** branch identity와
  archive 판정 수리는 필요하다. 이것만으로 사용자 요구 누락·시간·토큰 개선은 입증되지 않는다.
- **기존 구현 모양도 검사 계약에 고정됐다.** `config/skills/devlyn:resolve/SKILL.md:53`은
  모든 phase의 fresh worker를 요구한다. `scripts/lint-skills.sh:1318–1367`은 중복
  MECHANICAL 문구와 BUILD worker 문장을 검사한다. 구조 변경 시 동등한 행동 검사로 바꿔야 한다.
- **축약 후보가 제품 전환까지 이어지지 않았다.** 0124/0125의 미채택 결과는 보존하되,
  모든 후속 구조 실험을 영구 대기시키는 조건으로 삼지 않는다.

**Named delta:** 0114/0120의 적응형 방향을 뒤집지 않는다. 0196의 실제 full 비용과
검토 수리 증거, 0197/0198의 fresh 우위 부재, 이번 사용자 요청을 근거로 다음 단위를
“미세 결함 탐색”에서 **실행 가능한 축소 후보의 채택 결정**으로 바꾼다. 동결 결과는 재판정하지 않는다.

## 목표 제품과 삭제 순서

devlyn-cli는 Pyx 없이도 유용한 독립 코어다. 쉬운 작업에는 적은 추가 비용을,
어려운 작업에는 더 나은 검증 완료 결과를 제공한다. Pyx·OS·fleet은 선행조건이 아니다.
“완벽함” 선언 대신 요구 충족·실패 정직성·회귀·검증 완료시간·전체 사용량으로 판정한다.

후보는 **의도/제약 확인 → 한 실행 주체의 구현과 실제 검사 → 필요한 독립 검토 →
finding 재현·수정·재검증 → 근거가 붙은 완료**로 동작한다. 이는 고정 모델 호출
목록이 아니다. 같은 owner가 계획·구현·자신이 만든 잔여물 정리를 수행한다.

| 줄이거나 합칠 것 | 남길 책임과 구현 지점 |
| --- | --- |
| PLAN/BUILD/CLEANUP마다 의무적인 새 모델 호출 | owner의 판단과 기존 검사 도구로 수행한다. 먼저 0125 `fcacf908` delta를 현재 코드와 대조한다. owner로 이동한 명령 선택 추론도 비용에 포함한다. |
| 요구 복사·반복 보고서·judge에게 전달되는 조정용 지침 | 원문 요구·현재 diff·검사 결과·미해결 질문을 연결한다. 기존 `phase-prompt-render.py` projection을 재사용하되 judge의 원문·코드 접근을 보장한다. |
| 변경이 없어도 별도 추론하는 CLEANUP | owner의 scoped cleanup과 기계적 확인으로 합친다. 검사 후 코드가 바뀌면 관련 검사와 최종 판정을 무효화하고 다시 검증한다. |
| 엔진 가용성만으로 늘어나는 의무 검토 | 후보는 관찰된 요구 상호작용·검증 사각지대·결과의 중대성에 맞춰 추가한다. 현행 product pair 정책은 검증·이행 전까지 유지한다. |
| 모델이 상태 전이·증거 복사·보고서 조립을 반복하는 절차 | 기존 `_shared`의 검사·evidence·terminal·completion 함수를 직접 활용한다. 새 scheduler·DSL·graph DB를 만들지 않는다. |

어려운 작업에서는 해당 작업의 실패 가정을 검토한다. 예: 정상 동작과 rollback의
동시 충족, 소유권과 재시도의 충돌, 여러 호출자의 오류 계약, 실행 중 범위 위반.
검토자는 다른 판단을 보기 전에 원문·코드·실제 증거로 반례를 제시한다. owner는
재현·수정하고 관련 경로를 재검증한다. domain/file-count 분류나 거대 위험 점수기는 도입하지 않는다.

범위·사용자 제약, explicit engine fail-closed, 실제 실행 증거, 실패/인프라 구분,
독립 검토 접근권, 최종 source/evidence 일치, 안전한 전달 소유권은 남긴다.
`spec-verify-check.py`, process evidence, terminal 판정, `task-complete.py`를 우선
재사용한다. 임의의 사용자 제약까지 정적 검사로 완전 검증한다고 주장하지 않는다.
첫 제품 수정 전에 원문 요구·제약·허용 범위를 고정한다. 새 발견은 owner가 판단하며
구현자가 자신의 수정에 맞춰 수용 기준이나 `authorized_surface`를 사후 확대하지 않는다.

**Subtractive-first:** 불필요한 호출과 중복 전달 삭제 → 기존 커널 직접 활용 →
최소한의 연결부 추가 순서다. 누락된 검증이나 stale 결과를 완료로 승인하지 않는
책임을 유지한다. 관찰된 실패 없이 새 방어 계층을 추가하지 않는다.

이번 요청의 산출물은 계획이며 아래 구현·실험은 아직 시작하지 않았다.

| 순서 | 산출물 | 완료 조건 |
| --- | --- | --- |

수리 후 이 표의 중단 지점으로 돌아온다. 연구 도구 개선만으로 이정표를 닫지 않는다.

## 유한한 평가와 중단 기준

- **A: 강한 native.** 같은 model/effort·도구/저장소·시간 한도. 자체 검사·수정과
  native subagent 사용을 제한해 약한 baseline을 만들지 않는다.
- **B: 축소 후보.** 요청과 현재 증거로 필요한 검토를 선택한다.
- **C: native + 일반적인 독립 review→repair.** 같은 총예산의 단순 대안으로,
  하네스 고유 가치와 추가 검토의 가치를 구분한다. 개별 phase의 인과 실험은 아니다.

개발은 일상 1·중간 1·어려운 작업 2개, 확인은 2·2·4개다. 어려움은 결과를 보기
전에 요구 상호작용과 검증 난점으로 정한다. 최소 두 실제 코드베이스와 현재
lifecycle/installer 연구군 밖의 요청을 포함한다. native 실패를 보고 작업을 고르지
않는다. 후보 작성자는 확인 작업의 답안을 보지 않는다.

요청·평가 코드·참조/반례·actual model ID·권한·순서·시간/사용량 예산을 시작 전에
등록한다. 실패·retry·review·repair·recheck·owner를 포함한다. reasoning은 중복
계산하지 않고 input/cache/OUTPUT·청구 비용을 분리한다. 계측 누락은 하한/UNKNOWN으로
보고하며 전체 계측 없이는 비용 채택을 선언하지 않는다.
시간·사용량 효율은 대응하는 완전 해결 제품끼리 비교한다. 효율 경로에는 서로 다른
어려운 작업 최소 2개에서 총 4쌍 이상의 완전 해결이 필요하다. 0성공이나 빠른 거부는
효율 이득이 아니다. 실패를 포함한 전체 소비·완료율도 별도 제시해 성공 표본 선택을 드러낸다.

**권고 채택 기준 — 결과 보기 전에 최종 registration에 고정:**

1. 요구·범위·회복/오류를 먼저 평가한다. 후보가 추가한 파괴적 실패, 제약 위반,
   허위 완료 또는 HIGH/CRITICAL 잔존은 채택을 막는다. 성공·실패·정당한 거부·인프라를 분리한다.
   두 채택 경로 모두 A가 해결한 대응 작업을 보존하고, 각 난도에서 A보다 완전 해결이
   줄지 않아야 한다. 비용 감소가 native 대비 품질 저하를 상쇄하지 않는다.
2. 쉬운 작업은 native 대비 검증 완료시간과 OUTPUT 중앙값의 추가 비용 각각
   10% 이내를 목표로 한다. 불필요한 delegate가 없어야 한다. 소표본의 이 수치는
   보편적 보증이나 통계적 동등성 증명이 아니다.
3. 어려운 확인 8회에서 native보다 최소 2회 더 완전하게 해결하는 것을 품질 개선의
   출시 기준으로 제안한다. 또는 A와 C가 해결한 작업을 모두 보존하는 동일 이상
   요구 충족에서 C 대비 시간/OUTPUT 중 하나를 30% 이상 줄이고 다른 하나를
   악화시키지 않는 효율 개선 경로를 허용한다. 모든 seat·input/cache/output·도구를
   포함한 등록된 전체 비용도 C보다 나빠지면 안 된다. 청구 비용을 알 수 없으면
   시간/OUTPUT 개선으로만 표시하고 전체 비용 최소화 채택은 보류한다.
4. 품질 향상의 추가 비용은 같은 예산의 C와 비교한다. C가 B의 해결 작업을 보존하고
   추가 회귀 없이 시간/OUTPUT도 더 나쁘지 않으며 하나 이상 실질적으로 더 좋으면
   단순 경로를 채택한다. 두 번째 지원 엔진의 역할·오류 계약도 확인하고, 성능 주장은
   실제 측정한 엔진/작업에 한정한다.
5. **새 full resolve 호출은 비교군에도 계획하지 않는다.** 최신 no-resolve 지시를
   지킨다. 과거 full 수치는 진단 자료다. 새로 허용된 matched full 비교 없이는 full
   대비 동등성·절감률을 주장하거나 모든 기존 full 사용처를 자동 교체하지 않는다.

blind assessment와 실행된 반례를 결합하며 검사 PASS만으로 의미적 완료를 정하지
않는다. 도중 발견한 evaluator 결함은 원래 결과를 보존하고 전 arm에 동일하게
탐색 검사를 적용한다. 한 번의 수정 뒤 새 시험으로 갈 수 있으나 기존 시험을
소급 재채점하거나 실패한 후보에 무제한 새 기회를 주지 않는다.

상한은 **개발 24회 + 조건부 확인 48회**다. 지출 승인이 아닌 다음 등록의 상한이다.
native subcall 수와 시간/토큰 총예산도 함께 제한한다. 구체 예산·작업·계측이
없으면 실행하지 않고 그 부족분만 해결한다. 재설계는 최대 한 번이며 새 예산과
새 확인 자료를 요구한다. 이 상한에 자동 추가하지 않는다.

## 이름과 종료 결정

기존 기록은 ideate/resolve를 intent 등으로 바꿀 수 있다는 방향이며 특정 새 이름은
확정되지 않았다. **권고 명칭은 `/devlyn:intent`**다. 사용자는 목표를 전달하고
시스템이 실행·검토를 구성한다. ideate의 요구 정렬을 재사용하되 긴 spec이나
고정 phase가 모든 요청의 의무가 되지 않게 한다.

개명은 5번 제품 전환과 함께 한다. 기존 resolve의 명시적 full 실행·spec·verify-only·
엔진 선택 의미를 조용히 바꾸지 않는다. 옵션 매핑·변경 고지·설치 migration을
함께 정하고, 옛 계약 경로는 명시적으로 남기거나 버전 경계에서 종료한다.
서로 다른 새 구현 두 개를 영구 유지하는 방향은 피한다.

후보가 단순 native+검토보다 이득이 없으면 강제 phase graph를 기본 제품으로
확장하지 않고, 검증·scope·완료 도구를 native에 얇게 결합한다. 완전한 legacy 폐기는
지원 사용처와 migration 증거를 갖춘 뒤 결정한다. Mission1·외부 개발자 gate15·
세계최고/보편적 우위 주장은 계속 OPEN이다. 종료 기준은 **더 나은 사용 경로의
실제 배포 또는 이득 없는 후보의 명확한 종료**다.

외부 참고: [Anthropic](https://www.anthropic.com/engineering/building-effective-agents)의
필요에 따른 복잡성 추가, [OpenAI](https://openai.com/index/harness-engineering/)의
짧은 안내·필요할 때 읽는 문서·기계적 경계 검증. 설계 참고이며 후보 성능 증거는 아니다.
